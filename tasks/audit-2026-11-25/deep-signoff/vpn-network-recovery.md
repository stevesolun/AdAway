# Signed VPN recovery | API 30 | 2026-11-26

**Final disposition: both offline status defects verified fixed on the consolidated signed OTA, on Wi-Fi and LTE.** The same API 30 device and source fixture were used before and after. [Signed results](#consolidated-signed-ota) include Home, the notification shade, direct DNS and Chrome.

**Signed baseline: DNS recovered; offline status was misleading.** All 20 measured online UDP queries passed, including the first test query after each transition. ## Verified fault: active status with no tunnel

1. With Home open, protection on and validated Wi-Fi selected, disable mobile data, then enable Android airplane mode. At 02:06:56 UTC Android disconnected Wi-Fi 101 and VPN 102. No network agents remained. At 02:06:58 the ordinary UDP tool exited 4 before sending: `configure UDP: Cannot assign requested address` for `192.0.2.1`.
2. With no default network or tunnel, Home still showed **Protection active**; the switch stayed checked. Notification ID 20 still read **Ad-blocker VPN active** with **Pause**, not a waiting status. [Home](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/26-offline-settled.png), [OS state](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/offline-settled-state.txt), [alias result](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/offline-alias.json), [notification](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/offline-notification.txt).
3. Repeated from validated LTE 105 / VPN 109 at 02:08:57 UTC. Android again reported zero network agents. The actual [notification shade](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/34-offline-shade.png) showed the same active claim. After leaving and reopening Home, the [header](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/35-offline-reentry.png) still claimed active protection; [network state](../../../app/build/reports/audit-2026-11-25/vpn-network-recovery/offline-reentry-state.txt) was still empty at 02:09:15.

Expected distinction: it is correct to retain the user's **on** setting and automatically resume. The status should distinguish **waiting for network** from an active filtering tunnel. The offline bind failure is expected, not a lost DNS response. Neither finding implies traffic escaped filtering.
