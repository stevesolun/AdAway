## Findings

### NOV-VPN-01 - P1 - Android Always-On Start Intent Is Ignored

**Location:** [VpnService.java](../../app/src/main/java/org/adaway/vpn/VpnService.java), lines 125-142, especially 129 and 140-142. Boundary: [Command.java](../../app/src/main/java/org/adaway/broadcast/Command.java), lines 34-46. Manifest service declaration: `app/src/main/AndroidManifest.xml:144-153`.

**Source proof:** Only a null intent or an explicit private `COMMAND=START` reaches `startVpn()`. A non-null framework service intent has no such extra, so it resolves to UNKNOWN and returns START_NOT_STICKY without creating a worker or entering foreground. The manifest advertises the VPN service and does not opt out of always-on. Android documents system starts through onStartCommand and unflagged intents; [AOSP Android 11 startAlwaysOnVpn](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r1/services/core/java/com/android/server/connectivity/Vpn.java) constructs the service-action/package intent without application extras (lines 664-668). See [Android always-on lifecycle and opt-out contract](https://developer.android.com/develop/connectivity/vpn#always-on).

**Impact/repro:** With VPN mode and consent already prepared, stop the ordinary app-started service, then enable always-on in Android Settings. A system-only start cannot establish the tunnel. A boot receiver or previous app START can mask this; test the unflagged start in isolation. If lockdown is selected, a failed start also leaves network access blocked by Android.

**Fix/test plan:** Recognize the platform service action with no private command as a legitimate system start, preserving rejection of malformed private commands. Always-on must remain supported; opting out is not an acceptable resolution. Add an attached-service instrumentation case sending the actual framework-shaped intent, assert RUNNING plus TUN and foreground state, and retain tests for explicit STOP, null sticky restart, and invalid commands. Then have main verify Settings/boot behavior. Baseline lifecycle tests call VpnServiceControls.start(), which always supplies the private extra; the added regression is described in the follow-up above.

### NOV-VPN-02 - P1 - In-Flight Lookup Repopulates Invalidated Rule Cache

**Location:** [VpnModel.java](../../app/src/main/java/org/adaway/model/vpn/VpnModel.java), lines 79-81; cooperating paths at 46-50 and 139-140. Update boundary excerpts: `SourceModel.java:1668-1695`, `AdAwayApplication.java:104-107`.

**Source proof:** LruCache.create() reads the rule DAO outside the cache lock. invalidateRulesCache() only evicts entries already present; it has no generation/epoch or lock spanning lookup and publication. [Android's create contract](https://developer.android.com/reference/android/util/LruCache#create(K)) explicitly permits concurrent cache access. [AOSP Android 14 LruCache.get](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-14.0.0_r1/core/java/android/util/LruCache.java), lines 126-146, inserts the created value after create returns.

**Deterministic schedule/repro:** Pause a cache miss after the DAO has obtained an ALLOWED result but before create returns. Commit a BLOCKED rule and complete the normal invalidation. Release the paused lookup. Its old ALLOWED result is inserted into the now-empty cache; subsequent DNS queries keep forwarding until another invalidation or LRU eviction. The reverse transition can keep an explicitly allowed host blocked. This is persistent cache poisoning by an ordinary race, not a claim of remote exploitation.

**Fix/test plan:** Serialize the complete cache get/create operation with invalidation, or publish into a generation-bound cache that an old lookup cannot repopulate. Add latch-controlled instrumentation around the actual VpnModel/DAO boundary for both transitions. Verify a lookup begun after invalidation returns current truth, not merely that the originally in-flight request can finish. Existing VpnModelCacheInvalidationTest performs only sequential reads/updates and cannot falsify this race. This is unrelated to October's HTTP-client initialization fix.

### NOV-VPN-03 - P2 - Losing One Network Clears All Networks Of Its Transport

**Location:** [VpnService.java](../../app/src/main/java/org/adaway/vpn/VpnService.java), lines 367-375, with identity discarded at 395-405 and a Set<NetworkType> at 99/358-360.

**Source proof/repro:** Call onAvailable(WiFi A), onAvailable(WiFi B), then onLost(WiFi A), with no cellular network. Both available events collapse to one WIFI entry. Losing A removes WIFI entirely, invokes waitForNetVpn(), stops the worker and publishes WAITING_FOR_NETWORK although B is still up. No new onAvailable(B) is owed because B was already delivered. [Android NetworkCallback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback#onAvailable(android.net.Network)) specifies that registerNetworkCallback can report multiple networks; onLost is per matching network, not a transport-wide disconnect.

**Impact:** Multi-network same-transport handover can permanently drop filtering until another network event or explicit restart. No particular OEM callback sequence was reproduced in this pass; the accepted event sequence and resulting state loss are source-confirmed.

**Fix/test plan:** Track Network identities and their capabilities, removing only the lost identity. Add deterministic service/callback tests for A available, B available, A lost; duplicate notifications; B lost; and intentional stop followed by late callbacks. Confirm no stop while an eligible underlying network remains. Preserve October's vpnRequested/current-worker guards. Extend device coverage to same-transport handover and Ethernet transitions; transport-only WiFi/cellular tracking is also incomplete for Ethernet.

### NOV-VPN-04 - P2 - Resolver Snapshot Survives DNS And Default-Network Changes

**Location:** [VpnService.java](../../app/src/main/java/org/adaway/vpn/VpnService.java), lines 358-364 and 388-405. Snapshot/forwarding: [DnsServerMapper.java](../../app/src/main/java/org/adaway/vpn/dns/DnsServerMapper.java), lines 101-121 and 314-319; [VpnWorker.java](../../app/src/main/java/org/adaway/vpn/worker/VpnWorker.java), lines 395-404.

**Source proof:** Resolver addresses are read only when establishing a tunnel. The service registers availability/loss callbacks but implements neither link-property changes nor a default-network-change path. Gaining WiFi while cellular remains in the set does not reconnect. Protected sockets are not bound to the Network from which resolver addresses were obtained. [Android's link-properties callback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback#onLinkPropertiesChanged(android.net.Network,%20android.net.LinkProperties)) is the distinct notification for changed network link data.

**Repro:** Keep one WiFi Network alive, change its DNS server from reachable A to B, then make A silently drop traffic. With the default-disabled watchdog, new queries still go to A; expiry closes individual queries without rebuilding the mapping. A second case is cellular-to-WiFi default handoff while cellular remains available: fresh unbound protected sockets use the new default path with the old network's private resolver address. Exact user impact depends on old-resolver reachability.

**Fix/test plan:** Maintain the selected underlying Network plus current LinkProperties; react to effective DNS/default-network changes, bind upstream sockets to the resolver's Network or rebuild them coherently, and coalesce equivalent callbacks. Test same-Network DNS replacement and cellular/WiFi overlap with resolver A unreachable on B. Verify query delivery after transition and no stale callbacks after stop. NOV-VPN-03 addresses identity removal; fixing it alone does not refresh DNS.

### NOV-VPN-05 - P2 - IPv6 Provider Routes Depend On DNS Resolver Family

**Location:** [DnsServerMapper.java](../../app/src/main/java/org/adaway/vpn/dns/DnsServerMapper.java), lines 126-127, with gating at 106/372-376 and route list at 143-149. [VpnBuilder.java](../../app/src/main/java/org/adaway/vpn/worker/VpnBuilder.java), lines 73-75.

**Source proof:** includeIpv6 for provider blocking equals whether an IPv6 DNS alias subnet was created. That subnet requires an IPv6 upstream DNS-server address, not IPv6 internet connectivity. A dual-stack network can legitimately advertise only IPv4 resolvers. Even with the IPv6 preference enabled, that configuration omits every known-provider IPv6 /128 route while allowFamily(AF_INET6) permits IPv6 fall-through. [Android allowFamily contract](https://developer.android.com/reference/android/net/VpnService.Builder#allowFamily(int)) confirms the fall-through behavior.

**Impact/repro:** On a dual-stack network advertising only IPv4 DNS, use a listed provider's IPv6 endpoint, for example 2606:4700:4700::1111, from an included app. Its connection is not captured by the intended provider block routes, while the corresponding IPv4 address is captured. This is a hole for already-listed providers, not the known limitation that an IP list cannot cover all encrypted DNS. Live HTTPS behavior remains unexecuted.

**Fix/test plan:** Decouple IPv6 provider routes from upstream DNS family; keep ordinary IPv6 usable while consistently routing the configured provider set. Add configureVpn builder-capture tests for IPv4-only DNS on dual-stack connectivity with the preference both true and false, mixed DNS, and IPv6-only DNS. Main should verify installed /128 routes and included-app traffic. DnsServerMapperDohRoutesTest only tests caller-supplied booleans; it misses the production gating decision. October's IPv6-only resolver-retention fix remains intact.

### NOV-VPN-06 - P2 - DNS Instrumentation Cleanup Deletes Unrelated User Rules

**Location:** [DnsPacketProxyRuntimeTruthTest.java](../../app/src/androidTest/java/org/adaway/vpn/dns/DnsPacketProxyRuntimeTruthTest.java), lines 242-245, called at 92 and 98.

**Source proof/repro:** Every test's setup and teardown loops over SiteCompatibilityAllowlist.REQUIRED_DOMAINS and calls deleteUserFromHost. The DAO query at `HostListItemDao.java:38-39` deletes all USER rows for that hostname, regardless of type or fixture ownership. Seed a user redirect/block/allow for www.ynet.co.il, run even the unrelated exact-block test, and that row is removed with no restoration. The compatibility list includes 15 real domains, not test-unique names.

**Impact:** Test-only state corruption and order-dependent results on persistent emulator data; not an APK runtime defect. A disposable test database reduces user risk but does not make the fixture isolated.

**Fix/test plan:** Snapshot and restore affected original rows, or use an isolated database and test-specific compatibility data. Track inserted fixture IDs instead of deleting all matching real-domain USER rows. Add a harness that seeds distinct types/IDs and verifies identical rows before/after every test, including exceptional exits. Do not run this proof against a personal device. Existing unique-host cleanup in VpnDnsTunnelInstrumentedTest shows the narrower ownership pattern.

## Protocol, Lifecycle And Permission Trace

1. App commands flow from the signature-permission-protected CommandReceiver to the selected AdBlockModel on diskIO, then VpnServiceControls to the permission-protected VPN service. Manifest excerpts declare BIND_VPN_SERVICE, INTERNET, ACCESS_NETWORK_STATE and special-use foreground-service permissions. Notification pending intents are explicit and immutable. No unprivileged external service-start bypass was established. Framework starts are a separate input boundary (NOV-VPN-01).
2. START sets requested state and foreground STARTING, replaces the worker, and launches its packet/monitor tasks. Builder establishes consent-authorized TUN; null establishment throws SecurityException. RUNNING is emitted after successful establishment/monitor initialization. Stop/revoke clears requested state, stops the worker, cancels heartbeat and closes the interface. Handler events from retired workers are ignored. The same-transport and resolver-change defects remain outside those October guards.
3. Mapper snapshots underlying DNS, allocates documentation-address aliases and exact host routes, and adds provider-block routes. Builder excludes configured visible packages, keeps AdAway included, makes programmatic bypass opt-in, and allows both address families. This is a split-routing DNS filter, not an encrypted full-traffic VPN or universal DNS-enforcement layer.
4. Worker reads TUN, processor copies the actual packet bytes, and active DnsPacketProxy accepts directly represented UDP/53 standard single-question requests to exact aliases. Lowercased name resolves through VpnModel/DAO. BLOCKED gives local NOERROR/NODATA plus short-TTL SOA; REDIRECTED uses a numeric, QTYPE-aware A/AAAA answer or NODATA/SERVFAIL; ALLOWED forwards the original DNS bytes.
5. Forwarding protects then connects each socket to the selected resolver/53 before send. DnsQueryQueue owns pending queries; DnsQuery retains socket and independent poll descriptor, checks poll errors and receives only actual datagram bytes. Callback checks QR, ID, opcode and question before queuing reversed IP/UDP endpoints with corrected lengths/checksums. Queues drain on tunnel exit; expiry and capacity are bounded.
6. DohPacketProxy is not constructed by production code. Its legacy lookup-based synthesis, unprotected HTTP client and asynchronous lifecycle are not evidence that active AdAway DNS is encrypted. It must not be activated without a separate protocol/resource redesign.
